## Executive summary

This is a Django 5.2 monolith (`core`, `chat`, `kb`, `crm`, `dashboard` apps) serving an anonymous, session-token-based chat API consumed by a vanilla-JS embeddable widget (`static/widget/nordland-widget.js`). The client is **Nordland VVS** (`nordlandvvs.se`), a Swedish HVAC/VVS company servicing heat pumps (IVT, Bosch, and — per content files — Greenline/Vent product lines), water pumps/wells (Grundfos, Debe), and water filtration (Scandia Pumps, Aqua Expert, Aqua Invent). Currently deployed at `nordland.3dpresence.com` behind Caddy (auto-HTTPS) → gunicorn → Postgres, via `docker-compose.prod.yaml`.

The chat pipeline is a deterministic, code-owned finite-state machine (`chat/orchestrator.py`) — the LLM (Gemini 2.5 Flash/Flash-Lite, via Vertex AI, EU `europe-north1`) is called per-step but never controls state transitions. All agent behavior (prompts, models, temperature, guardrail rules, FAQ injection, routing rules) is DB-editable from a custom staff dashboard (`dashboard/`), live with no redeploy. Photo upload already exists end-to-end (attach → sanitize → Gemini vision extraction → nameplate/error-code parsing) but ONLY inside the existing chat turn loop — there is no separate upload endpoint, no async/background job, and no voice or telephony surface at all today. CRM lead capture, GDPR PII purge, and a two-tier guardrail (hardcoded keyword veto + LLM classifier) are implemented and reasonably mature. Test suite is pytest + pytest-django with a **content-aware mocked Gemini fixture** (`conftest.py`) — no real LLM calls in CI by default; a `live` marker opts into real Vertex calls.

Key planning implications up front: the SSE streaming endpoint (`chat/views.py`) is fully synchronous Django (WSGI/gunicorn, not ASGI despite `config/asgi.py` existing) — long-running voice/audio work will need a different transport. The chat API is anonymous and stateless-token-based (`Conversation.public_id`), which maps reasonably well to a phone-call session too, but nothing today associates a session with a phone number/WhatsApp identity except at the very end (contact capture during escalation). CORS is a hand-rolled allowlist (`WIDGET_ALLOWED_ORIGINS`), not django-cors-headers.

## 1. Chat pipeline end-to-end

### Turn flow (`chat/orchestrator.py`)
- `open_conversation(language)` creates a `Conversation` (see §1 models) with `case_state = new_case_state()` (from `chat/casestate.py`), sets `current_slot = "category"`, and returns the greeting + category chips.
- `process_turn(conversation, user_text="", image=None)` is the single entry point per user message:
  1. Hard ceiling: `cs["turns"] >= settings.MAX_TOTAL_TURNS` (default 25) → terminal message, no LLM call.
  2. Persists the user `Message` (text and/or `image`).
  3. If an image was attached, `_run_vision()` fires first (OCR/nameplate read via Gemini vision, independent of FSM state).
  4. `_advance()` runs the FSM loop (max 5 internal hops per turn) over `core.enums` states: `STATE_INTAKE → STATE_ROUTING → STATE_SPECIALIST | STATE_UNSUPPORTED → STATE_ESCALATE → STATE_RESOLVED`.
  5. Persists the assistant `Message`, flushes `CaseState` → `crm.Session` (`flush_to_session`), returns `{message, chips, state, decision, events, debug}`.

### State handlers
- **INTAKE** (`_intake_step`): fills `REQUIRED_SLOTS = ["category","problem","brand","model"]` one at a time. On a "rich" first message (`intake.looks_rich`), one bulk-extraction LLM call (`intake.bulk_extract`) pulls every fact at once. Free-text answers go through `intake.extract_answer` (chip-exact-match short-circuits the LLM; otherwise one cheap Flash-Lite call). After 2 failed re-asks, a slot is force-set to `"unknown"`. A "photo nudge" fires once if `model == "unknown"` and no nameplate photo yet. `is_routable(cs)` (in `casestate.py`) gates the transition to ROUTING once category+problem+brand/model (or nameplate photo) are known.
- **ROUTING** (`_route`): builds a trigram query from brand/model/OCR text, calls `kb.identification.identify_machine()`, then calls the router LLM agent (`_call_router`, prompt role `"router"`) to classify `severity`/`problem_category`. Checks `kb.models.RoutingRule` (admin-configurable) for an override (`route_maintenance` / `urgent_contact`) that can skip straight to escalation. If a `Machine` was identified → SPECIALIST, else → UNSUPPORTED.
- **SPECIALIST** (`_specialist_step`): loads the machine's PDF manual(s) via `chat/context.py` (Gemini context-cache when large enough, else inline bytes), renders the `"specialist"` prompt with brand notes + FAQ + problem + error code, calls Gemini (JSON response, optional "thinking" budget on complex cases), parses `{answer_to_customer, confidence, decision, in_docs, severity, report}`. Confidence is hard-capped when the machine match is weak (<0.4) or when the model itself flags `in_docs:false`. Runs `chat.guardrails.is_unsafe()` on the draft. Any of {unsafe, confidence < `CONFIDENCE_GATE=0.70`, decision != "solve", reply-budget exhausted (`REPLY_BUDGET=5` specialist turns)} → ESCALATE.
- **UNSUPPORTED** (`_unsupported_step`): calls the `"intelligent_intake"` agent (equipment we don't have a manual for) → always escalates with a qualified lead.
- **ESCALATE** (`_escalate_step` + `_begin_escalation`): a staged sub-flow — (a) one-time "please describe the problem more + send an error-code photo" diagnostic prompt (`await_diag`), (b) lazy contact collection over `CONTACT_SLOTS = ["name","phone","email","postal_code"]` with per-field sanitizers, (c) returning-customer detection via `phone_hash`, (d) approval gate (`_is_yes`/`_is_decline` regex parsing — no LLM), (e) on yes: `crm.leads.create_and_dispatch()` fires, session marked resolved.
- **RESOLVED** (`_terminal_step`): static "you're all set" message.

### LLM calls (`core/services/gemini.py`)
- Single client factory `make_client()`: **Vertex AI preferred** (project from `GOOGLE_CLOUD_PROJECT`, location default `europe-north1` for GDPR), **API-key fallback** (`GEMINI_API_KEY`, dev only). Has a custom clock-drift-correction shim (`ensure_clock_correction`) patching `google.auth._helpers.utcnow` because Windows/Docker clock drift breaks Vertex SA JWT signing.
- `generate()` — single-turn, non-streaming; supports `system_instruction`, `cached_content`, `response_mime_type`, `thinking_budget` (default 0 — thinking is explicitly disabled by default because it eats the output-token budget and truncates structured JSON).
- `generate_stream()` — exists (used nowhere found in orchestrator; the widget-facing SSE streaming in `chat/views.py` streams *events*, not partial LLM text — `process_turn` returns a complete message, only wrapped in SSE frames for transport).
- `file_part(path)` — inlines PDF/image bytes as a `Part` (Vertex does NOT support the Files API — code comment confirms this was verified in a "Phase 0 spike"). No GCS URI path implemented yet.
- `create_cache()` — Gemini context cache for large PDFs (`CACHE_MIN_TOKENS = 4096` floor in `core/constants.py`), TTL 3600s, cached by machine + docset hash in Django cache.
- `embed()` — Gemini embedding model with fallback chain, used by `kb/semantic.py`.
- Models: `core/constants.py` — `flash = gemini-2.5-flash`, `flash_lite = gemini-2.5-flash-lite`, `pro = gemini-2.5-pro` (unused), `embedding = gemini-embedding-2` (env-overridable). **3.x model ids all 404 on the current Vertex project** per a code comment — only 2.5 family confirmed callable as of 2026-06.
- Every agent role's actual model id is DB-driven (`kb.models.AgentPrompt.model_id`), read fresh each turn via `chat/prompts.py::model_for(role)` — code only supplies fallback defaults.

### Photo upload (current mechanism)
- **Endpoint**: same `POST /api/chat/<uuid:public_id>/message` (`chat/urls.py` → `chat/views.py::post_message`) — multipart form with `image` file field + `message` text field. No dedicated upload endpoint exists.
- **Sanitization**: `chat/uploads.py::sanitize_image()` — verifies real image via Pillow (`Image.verify()` then reopen), restricts to `{JPEG, PNG, WEBP}`, caps 8 MB, `Image.MAX_IMAGE_PIXELS = 40_000_000` (decompression-bomb guard), strips EXIF/GPS by re-encoding to JPEG q85 with no exif/icc passed through. Raw bytes are never persisted — only the re-encoded file.
- **Storage**: `Message.image` = `ImageField(upload_to="photos/")`, under `MEDIA_ROOT = data/uploads` (local disk, no S3/GCS abstraction).
- **Quota**: `MAX_IMAGES_PER_CONVERSATION` (default 8) enforced in `post_message` by counting prior `Message` rows with a non-empty image.
- **Reaching the LLM**: `_run_vision()` in the orchestrator loads the most recent image via `gemini.file_part(...)` (inline bytes) and does a single Gemini vision call with a strict "transcribe only what you see, four keys" system prompt to extract `{manufacturer, model, serial, error_code}`. Result fields are sanitized through `chat/sanitize.py::clean_model/clean_error_code/clean_lead_field` before being written into `CaseState.slots`. Also, `_history_parts()` re-attaches up to `max_imgs=4` of the conversation's prior images (as Gemini file parts) to EVERY downstream agent call (router, specialist, unsupported-intake) so photos aren't lost across turns.
- **CRM copy**: on escalation, `crm.leads.attach_customer_files()` copies every uploaded image from the transcript onto `crm.models.CustomerFile` (dedup by sha256) so photos survive later conversation purges.

### Session/case state machine
- `chat/casestate.py::new_case_state()` is the canonical shape: `state`, `current_slot`, `reask`, `slots` (category/problem/brand/model/error_code/serial/nameplate_photo/ocr_text), `contact` (name/phone/email/postal_code/consent), `contact_slot`, `awaiting_approval`, `escalation_reason`, `machine_id`, `match_confidence`, `problem_category_id`, `severity`, `decision`, `confidence`, `report` (troubleshooting_performed/resolved/service_recommended/booking_requested), plus orchestrator-added transient flags (`bulk_done`, `photo_nudged`, `diag_done`, `await_diag`, `asked_reach`, `returning`, `specialist_turns`, `turns`).
- This blob lives on `Conversation.case_state` (`JSONField`) and is **flushed every turn** into typed columns on `crm.models.Session` (`flush_to_session`) — Session is the canonical reporting store; admin-edited Session fields are never clobbered by later flushes (only orchestrator-owned facts are re-written).
- States are plain strings from `core/enums.py`: `STATE_INTAKE="INTAKE"`, `STATE_ROUTING="ROUTING"`, `STATE_SPECIALIST="SPECIALIST"`, `STATE_UNSUPPORTED="UNSUPPORTED_INTAKE"`, `STATE_ESCALATE="ESCALATE"`, `STATE_RESOLVED="RESOLVED"`.

### Guardrails (`chat/guardrails.py`)
Two layers, both enforced in code regardless of DB/prompt config:
1. **Keyword veto** (`_FORBIDDEN` regex) — hardcoded, blocks instructing electrical work (wiring/fuse box/mains/dangerous panels — but a plain filter-cover front panel is explicitly NOT vetoed), refrigerant work, pressure-system work, deep disassembly, combustion/flue work, legionella treatment. A comment explains the panel regex was tuned to keep "open the filter cover" allowed while still catching "open the control/service panel".
2. **LLM safety classifier** (`classify_unsafe`, role `"safety"`) — a second opinion on phrasing the keywords miss; defaults `unsafe=False` only on a clean parse, any exception → `unsafe=False` at this layer (the keyword veto is called the "hard gate").
3. **Output leak detection** (`_LEAK` regex) — catches echoed trust-boundary delimiters or "system prompt"/"these instructions" mentions.
Any hit forces `STATE_ESCALATE`.

Additive, staff-editable guardrails: `kb.models.AgentGuardrail` (role + rule text), appended via `chat/prompts.py::guardrails_block()` — explicitly documented as ADD-ONLY, cannot weaken the hardcoded baseline. The dashboard's Guardrails page (`dashboard/views.py::guardrails_page`) shows the hardcoded `_BASELINE_GUARDRAILS` read-only alongside these.

### Sanitization / trust boundary (`chat/sanitize.py`)
- `wrap_untrusted(text, kind)` — Microsoft "spotlighting": wraps any customer-supplied text in `<<UNTRUSTED kind="...">>...<<END_UNTRUSTED>>`, strips control chars, neutralizes override-style phrases ("ignore previous instructions" etc. → `[redacted]`). Used for conversation history, OCR text, problem descriptions, transcripts fed to the summarizer.
- Field validators: `clean_name`, `clean_phone` (normalizes to E.164, assumes Sweden +46 for a leading 0, rejects bare digits with no country code), `clean_email` (Django validator), `clean_postal`, `clean_model` (rejects sentence-like content), `clean_error_code` (shape regex requiring a digit), `extract_error_code` (pulls a code out of free text only when alarm-context words are present), `clean_lead_field` (generic CRLF/control-char stripper for anything bound for email/webhook/WordPress — prevents header injection).

### i18n (`chat/i18n.py`)
- Two-tier: (a) **templated bot strings** (greetings, intake questions, escalation prompts, chip labels) live in an in-code `T = {"en": {...}, "sv": {...}}` dict, looked up via `t(locale, key, **fmt)`. Adding a language = add a dict entry here + Swedish rows for chips/FAQ in the DB. (b) **free-form LLM replies** localize via a `{locale}` directive appended to every agent's prompt (`chat/prompts.py::render()` + `AgentPrompt.language_directive`, seeded as `LANGUAGE_DIRECTIVE` in `kb/seed_prompts.py` — "Respond to the customer ONLY in {locale}... Technical identifiers stay verbatim"). Staff dashboard UI strings use Django gettext (`.po` under `locale/sv/`), a THIRD, separate mechanism.
- `Conversation.language` is a fixed `CharField` set at session-open time (`LANG_CHOICES = [("en","English"), ("sv","Svenska")]`), not per-message. The widget's language switcher (`langSel` in the JS) restarts the session in the new language (`switchLang()` calls `openSession()` fresh) rather than switching mid-conversation.

## 2. Knowledge base (`kb/`)

### Data model (`kb/models.py`)
- `Vendor` (name, slug, `notes`, `agent_notes` — per-vendor guidance injected into the specialist), `Category` (self-referencing tree; `group` field is one of `CATEGORY_GROUP_CHOICES = [heat, air, water, hybrid, other]` — the dashboard's top-level KB grouping), `Machine` (vendor+category+model_name+aliases JSON; `search_text` denormalized lowercase blob rebuilt on every save, GIN trigram index `kb_machine_search_trgm`; `is_supported` flag), `MachineDocument` (PDF manual per machine+lang+kind, `parsed_text`, `token_estimate`, `sha256`), `BrandNote` (vendor± category scoped internal notes), `ProblemCategory` (controlled vocab per category, router emits the slug), `FAQEntry`/`FAQEntryText` (i18n per-language rows, fallback to `en` via `pick_text()`), `GenericGuide` (kind: faq/guide/best_practice, per category+lang), `QuickReplyChip`/`QuickReplyChipText` (intake-step chips, i18n), `AgentPrompt` (role, body, language_directive, model_id, temperature, thinking_enabled/budget, max_output_tokens, inject_faq, faq_categories M2M, prompt_version, is_active — **single source of truth for which model an agent uses**), `AgentGuardrail` (role, rule, is_active, order — ADD-ONLY per §1), `FlowConfig` (singleton JSON graph `{nodes, edges}` — a Vapi-style visual canvas that is a *documentation/config* surface over the real code FSM, not an execution engine — see `dashboard/views.py::default_flow_graph()`), `MachineNote` (per-machine staff notes, auto-injected), `PolicyDocument` (company terms PDFs, cited on booking/quote/maintenance/consumer-rights — explicitly NEVER injected into troubleshooting context), `RoutingRule` (admin conditions → `troubleshoot | route_maintenance | urgent_contact`, priority-ordered), `SiteFAQ` (imported from nordlandvvs.se's public FAQ, general non-machine-specific, fed via semantic search).

### Machine identification (`kb/identification.py`)
- Primary: Postgres `pg_trgm` — `TrigramSimilarity(search_text, query)` combined via `Greatest()` with a custom `WORD_SIMILARITY` SQL function (better for noisy OCR/free text containing the model as a substring). `DEFAULT_THRESHOLD = 0.30`.
- Fallback: `kb/semantic.py::semantic_identify()` (Gemini embeddings, cosine similarity, in-memory over a small corpus cached in Django cache keyed by content hash) — only engages when trigram is below threshold, gated by `settings.SEMANTIC_SEARCH_ENABLED` (on by default at runtime, off in tests). `SEM_IDENTIFY_THRESHOLD = 0.78` cosine to claim a machine; reported confidence is deliberately capped at `SEMANTIC_MATCH_CONFIDENCE = 0.65` (not the raw cosine) so downstream specialist gates still fire.
- Can be scoped to a known `Vendor` once the brand slot is filled (`identify_machine(query, vendor=...)`), which raises confidence for short model codes.

### Routing/escalation config layer
- `RoutingRule` — orchestrator checks this immediately after identification (`_match_routing_rule` in `orchestrator.py`), can force `route_maintenance` or `urgent_contact` (skips specialist troubleshooting entirely), matched on category / problem_category / severity / keyword substring, priority-ordered.
- `AgentPrompt` per role (`intake, router, specialist, intelligent_intake, summarizer, safety, qa` — `qa` role exists in `AGENT_ROLE_CHOICES` but is unused by the orchestrator, likely reserved for a v2 "hard cases" QA agent).

### Ingest (`kb/ingest.py`, `kb/management/commands/`)
- `ingest_pdf_bytes()` — shared by the CLI (`import_kb.py`, `ingest_pdf.py`) and the dashboard's KB Manager upload (`kb_doc_upload` view). Validates `%PDF-` magic bytes, 40 MB cap, `pdfplumber` text extraction (token estimate ~chars/4), sha256, replace-in-place support (deletes the superseded physical file). Not RAG — the specialist gets the **full PDF inlined into Gemini context** (or context-cached), `parsed_text` is only for token-estimate/audit/search, never retrieved chunk-by-chunk.
- `seed_kb.py` (idempotent) seeds: categories (`heat_pump` + 4 sub-types `water_to_water/air_to_water/air_to_air/exhaust_air`, `water_pump_well`, `water_filtration`), `VENDORS = ["IVT","Bosch","Grundfos","Debe","Scandia Pumps","Aqua Expert","Aqua Invent"]`, 5 seed machines (IVT 490/402 → exhaust_air; Bosch Compress 7000i → air_to_water; Grundfos SQ → water_pump_well; Debe DPM → water_pump_well), problem-category vocab, chips, one seed FAQ, and default `AgentPrompt` rows from `kb/seed_prompts.py::all_prompts()`.
- `seed_prompts.py` holds the full production prompt text for every role. Notable: the offline test mock (`conftest.py`) classifies calls by matching literal phrases inside these prompt bodies ("routing classifier", "senior Nordland VVS service technician", "service coordinator handling equipment we do NOT", "safety backstop") — **changing this wording breaks the mock without a docstring warning at both ends** (flagged in both files).

### Semantic search (`kb/semantic.py`)
Augmentation only, never primary: used for (a) machine ID fallback and (b) `rank_guides()` — ranks `GenericGuide` + `FAQEntry` + `SiteFAQ` snippets by cosine similarity to the customer's problem text, top-3 appended to the specialist's FAQ context (`chat/context.py::collect_knowledge`). Fails safe on any embedding error (empty result → caller keeps trigram-only behavior).

## 3. CRM (`crm/`)

### Models (`crm/models.py`)
- `Customer` — name/phone/email/address/postal_code/city/property_type/`consent_to_contact`; `phone_hash` is a peppered SHA-256 (`phone_hash()` function, pepper = `settings.PHONE_HASH_PEPPER`, must differ from `SECRET_KEY`) computed on every save, used ONLY for returning-customer lookup (never a reversible index). CRM-360 denormalized fields: `primary_machine`/`primary_category`/`primary_brand` FKs, `equipment_summary` (readable string, deterministically built), `profile_summary` (AI text, but only ever copied from an already-generated `Session.ai_summary` — never generated directly from Customer).
- `CustomerFile` — every photo/PDF a customer uploaded, copied out of the transcript (`unique_together = (customer, sha256)` for dedup), `source_message` FK back to the originating `chat.Message`.
- `Session` — 1:1 with `Conversation`, the canonical reporting row: denormalized manufacturer/model/serial/error_code (kept even if the FK `machine` is later nulled), severity, confidence_score, troubleshooting_performed (JSON list), resolved/service_recommended/booking_requested (nullable bools), `ai_summary`, decision, state, reply_turns, status (`active|resolved|escalated|closed`).
- `ServiceRequest` — the qualified lead, `idempotency_key` unique (stable hash of `public_id:reason:model:error_code`), `payload_json` snapshot, `escalation_reason`.
- `LeadDelivery` — one row per `(service_request, sink)`, `unique_together`, `status ∈ {pending,success,failed,skipped}`, `attempts`, `last_error` — this is the idempotency boundary for retries.

### Lead creation + sinks (`crm/leads.py`, `crm/sinks.py`)
- `leads.create_and_dispatch(session, reason)` — builds an AI summary (`build_summary`, wraps the transcript as untrusted DATA before summarization, role `"summarizer"`), copies files (`attach_customer_files`), creates-or-reuses `ServiceRequest` by idempotency key, calls `sinks.dispatch(sr)`.
- `sinks.SINKS = [DBSink(), EmailSink(), WebhookSink(), WordPressOffertSink()]` — each is independent; one failing never blocks another. `DBSink` always succeeds (the row itself is the record). `EmailSink` enabled iff `LEAD_EMAIL_TO` is set (console backend in dev). `WebhookSink` and `WordPressOffertSink` are **built but disabled** pending client-provided URL/field names (`LEAD_WEBHOOK_ENABLED`, `WORDPRESS_OFFERT_ENABLED`, plus `LEAD_WEBHOOK_URL`/`WORDPRESS_OFFERT_URL` — currently blank in `.env.example`). `dispatch()` is idempotent per `(request, sink)` (skips already-`success` deliveries) — this is the natural pattern to reuse for a future `n8n` webhook sink.
- `crm/management/commands/resend_leads.py` — presumably a cron sweep retrying non-success `LeadDelivery` rows (not read in full, but referenced from `DEPLOY.md` ops section: run every 10-15 min).

### Profile enrichment (`crm/profile.py`)
`enrich_customer_from_session()` — deterministic (never LLM-driven directly), copies the resolved `machine`/`category`/`brand` FKs + `ai_summary` onto `Customer`, rebuilds `equipment_summary` (distinct equipment across sessions, "IVT Geo 412C · Grundfos SQ" style). "Latest-escalated-session-wins" for the primary_* FKs.

### Analytics (`crm/analytics.py`)
Pure aggregation, no writes. `kpis()` (resolution/deflection/escalation/lead_capture/booking rates, avg turns, avg confidence), `contact_stats()` (returning customers via `phone_hash`-backed session count ≥2), `lead_health()` (delivery pipeline success rate by sink), `breakdowns()` (by group/severity/decision/status/vendor/top-machines/problem), `trend()` (daily gap-filled 7/30/90-day window), `success_metrics()` against hardcoded `TARGETS` (resolution 0.55, deflection 0.50, lead_capture 0.25, returning 0.20, delivery_success 0.95), plus per-entity stats (`vendor_stats`, `machine_stats`, `customer_stats`).

### PII / GDPR
- `crm/management/commands/purge_pii.py` — dry-run by default; `--days 365 --yes` deletes `Conversation` (cascades `Message`+`Session`) and `Customer` (cascades `CustomerFile`, with best-effort physical file deletion first) older than the cutoff. Meant to run monthly via cron.
- `PHONE_HASH_PEPPER` kept distinct from `SECRET_KEY`.
- Vertex location fail-closed to `europe-*` in production unless `ALLOW_NON_EU_RESIDENCY=1` (see `config/settings.py`, §9 below) — a **hard constraint on any new AI integration** (ElevenLabs/Vapi region choice must also respect this posture, or the client needs to explicitly accept non-EU processing).

## 4. Escalation / handoff to human — the actual mechanism

Three independent triggers converge on `STATE_ESCALATE`, all inside `chat/orchestrator.py`:
1. **RoutingRule override** (`_route` → `_match_routing_rule`) — admin-configured, category/problem_category/severity/keyword match → `route_maintenance` or `urgent_contact` action, bypasses the specialist entirely.
2. **Specialist gate** (`_specialist_step`) — `unsafe (guardrails.is_unsafe) OR confidence < 0.70 OR decision != "solve" OR specialist_turns >= REPLY_BUDGET(5)` → escalate. `escalation_reason` is set to one of `guardrail-classified reason string | "low_confidence" | "budget" | "decision"`.
3. **Unsupported equipment** (`_unsupported_step`) — no machine identified at all → always escalates, `escalation_reason = "unsupported"`.

Once in ESCALATE, `_begin_escalation`/`_escalate_step` run a fixed sub-flow: one-shot diagnostic enrichment (problem detail + error-photo prompt) → lazy contact slot-filling → explicit yes/no approval (`_is_yes`/`_is_decline`, pure regex, no LLM call) → on approval, `crm.leads.create_and_dispatch()` fires and `Session.status = "escalated"`. There is **no live-agent handoff / warm transfer** anywhere in code — "escalation" always means "create a `ServiceRequest` lead for a human to follow up asynchronously," never a synchronous human-in-the-loop takeover of the chat. This is the single most important fact for planning Vapi phone integration: today's "escalate" = async lead, not "connect this call to a human right now."

## 5. Widget (frontend)

### Files
- `static/widget/nordland-widget.js` (~540 lines, vanilla JS, IIFE, no deps, scoped `.nl-` CSS classes injected via a `<style>` tag). `static/widget/i18n/{en,sv}.json` provide the widget-chrome catalog (`loadI18n()` overlays defaults). `static/brand/nordland-logo.png` used as the header avatar.
- `templates/widget_demo.html` — the "simulated WordPress site" homepage; embeds the widget with `data-open="1"` (auto-opens on load). Served at `/` and `/widget-demo` (`core/urls.py` → `core/views.py::widget_demo`).
- `templates/playground.html` — a local/demo-only test console (chat + FSM debug inspector), served at `/playground`, gated by `settings.DEMO_OPEN_ADMIN or settings.DEBUG` (404s otherwise — **hidden in production**).

### Embed mechanism
Single `<script>` tag, e.g.:
```html
<script src="https://nordland.3dpresence.com/static/widget/nordland-widget.js" data-lang="sv" defer></script>
```
`data-lang` sets the initial language; `data-open="1"` auto-opens the panel (used on a dedicated chat landing page). The script derives its own API origin from `document.currentScript.src` (`API = new URL(script.src).origin`) — so the widget always calls back to whatever host served the JS file, not a hardcoded URL. This means **the homepage clone (item 1) can embed the exact same script tag pointed at the Nordland backend** with no code change, as long as `WIDGET_ALLOWED_ORIGINS` (CORS) is updated to include the clone's origin.

### API contract (from `chat/urls.py` + `chat/views.py`)
- `POST /api/chat/session` — body `{"language": "en"|"sv"}` (JSON) → `{public_id, message, chips, state}`. Rate-limited per IP (`RATE_LIMIT_SESSION`, default 20/window).
- `POST /api/chat/<uuid:public_id>/message` — body either JSON `{"message": "..."}` or multipart form (`message` field + optional `image` file). Returns `text/event-stream` (SSE) with frames: zero-or-more `{"type":"tool_result"|"routing_rule"|"escalate", ...}` events (from `_run_vision`/`_route`/specialist), an optional `{"type":"notice", "message":"Image not accepted: ..."}` if the image failed sanitization, then `{"type":"message", "message", "chips", "state", "decision", "debug"?}` (debug only if `DEMO_OPEN_ADMIN or DEBUG`), finally `{"type":"final"}`. Rate-limited per session AND per IP (`RATE_LIMIT_MESSAGE`, default 40/window; IP limit is 3× that).
- No auth on either endpoint — anonymous by design, `public_id` (UUID) is the bearer token. CORS handled by `core/middleware.py::WidgetCorsMiddleware` (hand-rolled, allowlist from `WIDGET_ALLOWED_ORIGINS`, only applies to `/api/` paths, handles `OPTIONS` preflight itself).
- Response is **not token-streamed from the LLM** — `process_turn()` runs to completion server-side (including all LLM calls) before the SSE frames are emitted; the "streaming" is purely a UX trick (typing-dots bubble replaced by the final text) plus a channel for the tool-result events. This matters for planning ElevenLabs voice: there's no existing partial-token stream to hook TTS into; you'd either wait for the full text (adds latency to voice) or need genuine LLM streaming added.

### Current features (per widget JS + recent git log)
- Floating launcher bubble with unread badge, "Chat with us" nudge callout pointing at the bubble when closed (`.nl-nudge`), full keyboard trap + `Escape` to close, `prefers-reduced-motion` respected.
- sessionStorage-persisted transcript/chips/session-id/open-state, namespaced per language (`STORE_KEY = "nordland-chat:" + LANG`).
- Quick-reply chips rendered from the backend response; chips clear as soon as the user starts typing free text.
- File attach (`fileInput.accept = "image/*,application/pdf"`, 10 MB client-side guard `MAX_FILE`, mirrored server-side by `chat/uploads.py` at 8 MB) — attaches as a "pending file" chip before send, sent as multipart with the next message.
- In-widget language selector (`langSel`) — switching restarts the session fresh in the new language (loses any accumulated slots server-side, since a new `Conversation` begins).
- Per git log: "cascade chips" (category → brands-with-manuals-in-category → a few models of that brand, capped at 6, excluding remote-control accessories) implemented in `chat/intake.py::chips_for()`; brand chips are "brands we service in this category" (any `Machine`, not filtered to only-manualed) so an unlisted brand still escalates to a lead; multi-fact intake + guided troubleshooting per the same log.

## Constraints & gotchas for planners

1. **Synchronous WSGI, not ASGI.** `Dockerfile` runs `gunicorn ... config.wsgi:application` with 3 workers. The SSE chat endpoint already ties up one worker thread per open connection for the duration of a turn (LLM call included). Voice (persistent duplex audio) or many concurrent Vapi/WhatsApp webhook calls will need either a much larger worker/thread pool, a move to ASGI (`config/asgi.py` already exists but is unwired), or — more likely — a **separate lightweight service** for the voice/telephony leg that calls back into this Django app's existing turn logic (or a shared library) rather than trying to hold voice sessions open inside gunicorn workers.
2. **No real token streaming from the LLM.** `process_turn()` computes the full reply before any SSE frame is sent. Voice needs either (a) accept the added latency of "wait for full text, then TTS," or (b) add genuine streaming (`gemini.generate_stream` exists in `core/services/gemini.py` but is never called from the orchestrator) — a nontrivial FSM refactor since `_specialist_step` etc. currently parse the complete JSON response synchronously.
3. **`CaseState` + turn model assumes one message = one turn = one FSM step**, with hard ceilings (`MAX_TOTAL_TURNS=25`, `REPLY_BUDGET=5` specialist turns). A phone call or WhatsApp thread that spans many more turns, or where a single "turn" is a longer spoken utterance, will hit these ceilings sooner than expected — revisit the constants (env-overridable, at least) before enabling voice/WhatsApp.
4. **Escalation = async lead, never live handoff.** Nothing in the codebase transfers a conversation to a human in real time. A Vapi phone call that needs a warm transfer to a human technician is a **new capability**, not a repurposing of `_escalate_step`. Chat-widget/WhatsApp "escalation" will still correctly mean "create a `ServiceRequest` and a human follows up later" — but voice almost certainly needs actual call transfer, which is entirely unaddressed today.
5. **Photo upload is coupled to the synchronous chat-turn request/response cycle**, not a standalone endpoint. WhatsApp image-in and any future async photo pipeline (e.g., MMS via Vapi, or an n8n-triggered upload) will need a new ingestion path that still funnels into the same `sanitize_image()` → `_run_vision()` → `CaseState.slots` pipeline (reuse those functions, don't duplicate the OCR/sanitization logic).
6. **No auth on the chat API** (`public_id` UUID is the only "token," anonymous by design). This is fine for a widget but is the wrong trust model for a webhook (Vapi/WhatsApp/n8n) endpoint — those need signature verification or shared-secret auth, which doesn't exist anywhere in the codebase yet (contrast with the CORS-based trust model for the widget).
7. **Vertex AI region is fail-closed to `europe-*` when `DEBUG=0`** (`config/settings.py`, raises `ImproperlyConfigured` unless `ALLOW_NON_EU_RESIDENCY=1`). Any new AI vendor (ElevenLabs, Vapi's own LLM/telephony infra) should be checked against the same GDPR posture the client evidently cares about — this constraint doesn't auto-extend to non-Gemini calls, so it needs an explicit decision, not an assumption.
8. **The Flow builder (`dashboard/flow.html` + `FlowConfig`) is decorative** — it looks like exactly the right place to add Vapi call-flow / voice-node configuration, but today editing it has **zero effect on runtime behavior** (the orchestrator FSM is 100% hardcoded in `chat/orchestrator.py`). Don't assume wiring a new node type there does anything until the FlowConfig→runtime gap is closed, or plan to close it as part of this work.
9. **Prompt-text-to-test-mock coupling is fragile.** `conftest.py`'s `_classify()` and `kb/seed_prompts.py` both hardcode the exact matched phrases (documented in both files). Any new agent role (e.g., a `"voice"` or `"whatsapp_intake"` role) needs its own unique classifier phrase added to `_classify()` or the mock will silently fall through to the generic `"OK"`/default response, masking bugs in tests.
10. **i18n is three separate mechanisms** (in-code `T` dict for templated bot strings, `{locale}` prompt directive for free-form LLM replies, Django `.po` gettext for dashboard chrome) plus per-message-none — `Conversation.language` is fixed at session-open. A phone call (language may need to be detected from speech, not chosen from a UI dropdown) and WhatsApp (language may need to switch mid-thread more gracefully than "restart the session") both stress this assumption.
11. **Widget CORS is a hand-rolled allowlist**, not `django-cors-headers` — only covers `/api/*` paths and only `POST`+`OPTIONS`. A homepage clone on a new origin needs that origin added to `WIDGET_ALLOWED_ORIGINS`; a Vapi/n8n webhook will bypass this middleware entirely (different path prefix) and needs its own auth story (see point 6).
12. **Media storage is local disk** (`MEDIA_ROOT = data/uploads`, bind-mounted in compose) — no S3/GCS. WhatsApp image URLs or Vapi call recordings will need either downloading into this same local-disk model or a storage-backend change; nothing pluggable exists today (`ImageField`/`FileField` with the default `FileSystemStorage`).
13. **`nordland.sql`** at the repo root is an unexamined Postgres dump that may hold the real production KB (per `DEPLOY.md`'s recommended migration path) — a planner building the homepage clone or a richer test suite should load and inspect it rather than relying solely on `seed_kb.py`'s minimal 5-machine seed catalog, since production content (including the Greenline/Geo/Vent lines referenced by the loose `.txt` files at repo root) likely lives there and not in the seed script.
14. **Rate limiting is a simple fixed-window cache counter, fails open if the cache is down** (`chat/views.py::_rate_ok`) — acceptable for a widget, but a public Vapi/WhatsApp webhook will need stronger idempotency (there is a pre-existing idempotency pattern to reuse: `ServiceRequest.idempotency_key` / `LeadDelivery` unique-per-sink — the bus-is-at-least-once discipline from the user's own global rules applies directly here).
